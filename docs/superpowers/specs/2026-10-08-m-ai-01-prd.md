# M-AI-01 PRD — Field Q&A on this project

**Status:** Saved for return (2026-10-08). Not a build GO.  
**Milestone:** `WS-AI / M-AI-01`  
**Policy:** `docs/superpowers/plans/2026-08-19-post-rc-boring-loop.md`  
**Planning brief (options, not this PRD):** `docs/superpowers/plans/2026-08-24-m-ai-01-query-gateway-planning-brief.md`  
**Sequence:** After `M-AUTHZ-02`. Do not start implementation before that membership work, or before the planning checklist in the brief is complete and a written go-ahead covers any live query table or meter.

A worker or PM asks a question about the job they already have open. The answer cites a record on that job, or it says it does not know.

## Problem

On site, the person holding the phone needs an answer from this job’s own tasks, photos, and activity. Searching the list is slow, and a guess that mixes in another job is a safety defect. The Create Task language model that already runs in the app is a form helper. It is not this product, and its key must not be reused for questions.

## Who it is for

Anyone who can already open the project can ask. That includes the worker on the tools and the PM reviewing the job. A guest added under `M-AUTHZ-02` can ask only about records they can already open. A company admin who is not on the job cannot ask about it. Starter and Pro both get the feature. The difference is how many questions a company can ask in a month, not who is allowed to ask.

## Outcome

The user is on one project. They ask in plain language. The app answers from that project only, and every factual sentence points at a task, an activity, or a photo they can open. If those records do not support an answer, the app says it does not know and does not fill the gap. The question and the answer are stored. The company’s monthly count goes up by one. The phone never holds a model key.

## What the answer is allowed to use

The corpus for this slice is this project’s tasks, task activity, and photo records the asking user can already read. A photo may be shown as the picture they could already open. The model does not look at the pixels and does not describe what it thinks the photo shows.

Submitted daily reports join the corpus only after `M-DAILY-01` actually submits them. Until then they are absent. Drawings, spec PDFs, and fastener checks are later slices (`M-AI-02`, `M-AI-03`, document register). They are not retrieved here.

## How a question runs

1. The app sends the question, the open `project_id`, and the user’s session. It may also send a task id when the question was started from that task.
2. The server checks that this user can read that project. A wrong or missing project never reaches the model.
3. The server runs a fixed set of reads in that user’s name: search tasks, read one task, read its timeline, read evidence metadata. No free-form SQL. No service-role read of another company’s rows.
4. Those rows go to one completion on a cheap model, with a size cap. The model either cites those rows or abstains.
5. The phone shows the answer, the citations, and the photos the user could already open. Tapping a citation opens that task or photo.

One retrieval and one completion. There is no multi-step agent on the phone. A question asked on a bad network waits until the request succeeds. It does not invent an answer offline.

## Cite or abstain

A factual claim names the record it came from: task, activity, or photo. The user can open that record and see the same fact.

The app abstains when the reads return nothing, when the rows disagree, or when the question needs a drawing, a measurement, or a judgment the rows do not contain. The abstain text says it does not know from this project’s records. It does not suggest a likely answer.

Wrong-project content in an answer is a failed release, including a test that asks as user A about project B.

## Where it sits in the app

Ask is an action on the project the user already has open, from Activity or from a task. It is not a fourth root tab. Starting from a task limits the first read to that task, then the rest of the same project if that task does not contain the answer. The project in the request is the project on screen. The user does not pick a different job inside the question.

## Caps

Questions are not task entries and do not spend the entries meter. They spend an internal monthly question count per company, enforced on the server. Starter has a lower cap than Pro. Near the cap, the app says how many are left. At the cap, the next question is refused and no model call is made. The cap can be changed without shipping a new app binary. Exact Starter and Pro numbers are a billing choice before build, written against plan price so a busy Starter company cannot spend the plan on questions. Per-question pricing is not this slice.

## Out of scope

- Any change to same-company task, photo, or report behavior.
- Starting before `M-AUTHZ-02` is in place. A partner on a job is limited to records they can already open.
- Moving the Create Task language model. That helper stays a separate, human-confirmed form fill. This slice does not put a model key in the app.
- Inferring drawings, passing hardware from a photo, or answering from a spec PDF.
- Embedding the project into a vector index.
- A customer API key or a customer MCP connection. An internal tool may call the same server later. Customers do not get that.
- An AI cost screen in Owner HQ. The query log is there for `M-OPS-03` to read later.
- The service role on the phone.

## Human gate

A live read function, a query log table, and the monthly meter wait for a written go-ahead before they are applied. The phone screen can be designed against a fixture before that. Shipping to a real project waits until wrong-project tests fail closed and a cited answer opens the record it names.

## Acceptance

1. A member of project A asks a question whose answer is in a task on A. The reply cites that task. Opening the citation shows the same fact.
2. The same member asks about something not in A’s tasks, activity, or photos. The reply says it does not know. It names no other project.
3. A member of project A asks with project B’s id. The server refuses before any model call. The reply contains no row from B.
4. A question started from a task cites that task when the fact is on it.
5. A photo citation opens a photo that user could already open. The answer text does not claim what the image depicts beyond the stored caption or task text.
6. The phone build contains no model key. The question count for the company increases by one on a successful ask, and does not increase the entries meter.
7. At the company cap, the next question is refused and the model is not called.
8. Two people of the same company, and later a partner who can already open a record, see citations only for records they can open. A partner who cannot open a task does not receive that task in an answer.
