## Failures @ 7986e9b

### P07 — Create Task form reopen prior-selected assert

**Flow:** `P07-form-plus-preserves.yaml`  
**Fail step:** `_assert-prior-selected-1` after `_reopen-library-from-form`  
**Error:** `Assertion '".*1 selected.*" is visible' failed`  
**Surface:** Hybrid `capture-session__library_grid` visible  
**Evidence:** `P07-BLOCKER.md`, `P07-FAIL-assert-prior-1-selected.png`

**Root cause:** Hybrid `HybridLibraryPickerScreen` title shows:
```tsx
{selectedCount > 0 ? `${selectedCount} selected` : "Select photos"}
```
When reopening from create-task form, `selectedCount` state needs time to sync and reflect the preserved selection from prior visit. The immediate `assertVisible ".*1 selected.*"` races with state update. Screenshot evidence shows "Select photos" title with checkmark on tile_0, proving selection IS preserved but title hasn't updated yet.

**Fix:** Add 5s `extendedWaitUntil` for ".*1 selected.*" on hybrid branch before moving to final assert:
```diff
 - runFlow:
     when:
       visible:
         id: "capture-session__library_grid"
     commands:
       - extendedWaitUntil:
           visible:
             id: "capture-session__library_grid"
           timeout: 8000
+      # Hybrid: wait for selectedCount to sync (title updates from "Select photos" to "1 selected")
+      - extendedWaitUntil:
+          visible: ".*1 selected.*"
+          timeout: 5000
```

**Why P04/P05 didn't hit this:** Those flows reopen from **selection screen** (`_reopen-library-from-selection`), not from **form**. Different entry point may have different state propagation timing.

### U05 — Update Progress form reopen testID mismatch

**Flow:** `U05-form-plus-preserves.yaml`  
**Fail step:** `_reopen-library-from-form` — `scrollUntilVisible id: update-progress__take_photo`  
**Error:** `No visible element found: id: update-progress__take_photo` (timeout 20000ms)  
**Evidence:** `U05-BLOCKER.md`, `U05-FAIL.png`

**Root cause:** `_reopen-library-from-form` helper was using wrong testID. The actual button on `ReportReplyComposer` is `report-reply-composer__photo`, not `update-progress__take_photo`. Cross-reference:
- `_open-library.yaml`: taps `report-reply-composer__photo` ✅
- `_confirm-selection.yaml`: waits for `report-reply-composer__photo` ✅
- `_reopen-library-from-form.yaml`: was looking for `update-progress__take_photo` ❌

**Fix:** Correct testID in both helper and flow:
```diff
 # _reopen-library-from-form.yaml
 - scrollUntilVisible:
     centerElement: true
     element:
-      id: "update-progress__take_photo"
+      id: "report-reply-composer__photo"
     direction: UP
 - tapOn:
-    id: "update-progress__take_photo"
+    id: "report-reply-composer__photo"

 # U05-form-plus-preserves.yaml (form-return assert)
 - assertVisible:
-    id: "update-progress__take_photo"
+    id: "report-reply-composer__photo"
```

## Technical Notes

### Hybrid vs Legacy Timing Differences

The hybrid `CaptureSession` library uses React state (`selectedCount`) to drive the header title, while the legacy `InAppLibraryPicker` may have different timing characteristics. When reopening from **selection screen**, the state is already "warm" from the prior visit. When reopening from **form**, the library component remounts or rehydrates, and `selectedCount` takes an extra render cycle to reflect the preserved selection.

### TestID Audit Lesson

Update Progress flows had inconsistent testID usage:
- Initial open: `report-reply-composer__photo` ✅
- Confirm landing: `report-reply-composer__photo` ✅
- Reopen from form: `update-progress__take_photo` ❌ (wrong, never existed)
- Final assert: `update-progress__take_photo` ❌ (copied from reopen)

**Recommendation:** Grep testID patterns across all helpers when introducing new surfaces to catch drift early.
