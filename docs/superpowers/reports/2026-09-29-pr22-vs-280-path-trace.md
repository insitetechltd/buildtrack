# PR #22 vs Build 280 Path-Trace Analysis

**Date:** 2026-09-29  
**Branch:** `cursor/fix-hybrid-photokit-thumbs-e7a1` (PR #22)  
**Baseline:** Build 280 (`1b944b7` on main)  
**PR Tip:** `547c430`  
**Context:** Build 280 IPA/device paints Recents thumbs correctly. PR #22 forever-gray on Debug iphonesimulator .app.

## Executive Summary

Build 280 (IPA Release on device) successfully paints PhotoKit thumbs. PR #22 branch (`cursor/fix-hybrid-photokit-thumbs-e7a1`) at `547c430` shows forever-gray tiles on Debug simulator builds but the same code **may work** on device Release builds.

**Critical finding:** The PR branch introduced **9 substantive architecture changes** to the PhotoKit native module between `1b944b7` (build 280 baseline) and `547c430` (PR tip). These changes fundamentally altered the image request pipeline, delivery mode, fetch ordering, and authorization flow.

**Key delta:** Build 280 used a **two-pass fast→sharp** delivery strategy with `.fastFormat` first (256px), then opportunistic upgrades to 512px. PR #22 switched to **single-pass** `.opportunistic` 512px requests with different authorization and sort behavior.

## Comprehensive Delta Analysis

### 1. Swift PhotoKit Module Architecture

**File:** `modules/photokit-thumbs/ios/PhotokitThumbsModule.swift`

#### Change: Fetch Ordering (Sorted vs Physical Unsorted)

**Build 280 baseline:**
- Recents: unsorted fetch (physical oldest-first), **reversed in-memory** for display
- `fetchOptions(sorted: false)` for Recents
- `recentsPhysicalOptions()` helper for Camera Roll physical order
- `newestRecents()`: walk backwards from physical end, filter images inline (max 8× scan)
- Comment: "TF 220: `creationDate` sort cost ~7s before first bind"
- Display index 0 = `result.object(at: count-1)`

**PR #22 (547c430):**
- **Always sorted** by `creationDate` descending (newest first)
- `fetchOptions(sorted: true)` for all albums (Recents + named)
- Physical unsorted helpers **deleted**
- `newestRecents()`: `fetchLimit` + sorted fetch, enumerate forward
- `reversed: false` everywhere (compatibility flag retained but never true)
- Comment changed to: "Sorted fetch ensures newest photos first, matching Photos app behavior"

**Impact on simulator vs device:**
- **Hypothesis:** Simulator Photos library fixture order may differ from sorted `creationDate` order
- Device: real Photos.app with valid `creationDate` metadata
- Simulator: synthetic fixtures may lack proper `creationDate` or return zero results after sort

---

#### Change: Delivery Mode (Fast→Sharp Two-Pass vs Single-Pass Opportunistic)

**Build 280 baseline:**
- **Two-pass delivery:**
  1. `makeOptions()` → `.fastFormat` (degraded fast path, 256px via `fastThumbPixel`)
  2. `makeSharpOptions()` → `.opportunistic` (degraded + final, 512px via `maxThumbPixel`)
- `fastTargetSize()` caps at `min(requested, 256, 512)`
- `targetSize()` caps at 512
- `sharpLimit = 3` concurrency cap for HQ upgrades
- `acquireSharpSlot()` / `releaseSharpSlot()` slot queue for viewport sharpen
- `applyIfSharper()` replaces bitmap only when incoming > displayed pixels
- First `onPainted` fires after `.fastFormat` 256px arrives
- `scheduleSharpUpgrade()` runs after fast paint if `sharp > fast + 0.5`
- Opportunistic = degraded bitmap first, then final full-quality

**PR #22 (547c430):**
- **Single-pass delivery:**
  - Only `makeOptions()` → `.opportunistic` (was `.fastFormat`)
  - No `makeSharpOptions()` (deleted)
  - No `fastThumbPixel` / `fastTargetSize()` (deleted)
  - Only `maxThumbPixel` = 512px
  - No slot queue (`sharpLimit` / `sharpInflight` / `sharpWaiters` deleted)
  - No `acquireSharpSlot()` / `releaseSharpSlot()` machinery (deleted)
  - No `applyIfSharper()` / `displayedPixel` tracking (deleted)
- `onPainted` fires when **any** opportunistic bitmap arrives
- Progressive paint controls decode rate (no explicit slot cap)

**Impact on simulator vs device:**
- **Hypothesis:** `.opportunistic` on simulator may fail to deliver **any** bitmap (not even degraded)
- Device: PhotoKit `.opportunistic` successfully returns degraded + final bitmaps
- Simulator: PhotoKit may require `.fastFormat` to return **anything** (synthetic fixtures?)
- Build 280's `.fastFormat` 256px guaranteed a bitmap; PR #22's `.opportunistic` 512px may stall on sim

---

#### Change: Network Access & Authorization

**Build 280 baseline:**
- `isNetworkAccessAllowed = false` (local only)
- **No authorization check** before `openLibrary` / `openLibraryLimited` / `openLibraryWithIds`
- Sync `openLibraryWithIds` Function (blocking)

**PR #22 (547c430) via commit `4240a54`:**
- `isNetworkAccessAllowed = true` (iCloud photos)
- **`ensureAuthorized()`** async function added:
  - Checks `PHPhotoLibrary.authorizationStatus(for: .readWrite)`
  - Requests auth if `.notDetermined`
  - Returns `false` if `.denied` / `.restricted`
  - Guards all three `openLibrary*` functions
- `openLibraryWithIds` → `AsyncFunction` (async/await)

**Impact on simulator vs device:**
- **Hypothesis:** Simulator may auto-grant Photos auth; device requires user prompt
- PR #22's `.readWrite` auth may be **stricter** than implicit read-only access
- Build 280 relied on **no explicit auth** (may have used app-wide `.authorized` state)
- If simulator auto-grants but the auth flow is broken, `ensureAuthorized()` may return `false` → `token: 0` → forever-gray

---

#### Change: Prop-Order Request Triggering

**Build 280 baseline (`PhotokitThumbView.swift`):**
- Props: `assetId`, `index`, `token`, `pixelSize`
- **Only `assetId` prop calls `requestIfNeeded()`**
- `index`, `token`, `pixelSize` props set values **without** calling `requestIfNeeded()`
- Assumption: `assetId` is last prop set (after token/index/pixelSize)

**PR #22 commits (multiple iterations):**
- Commit `7ada651`: Add comprehensive prop-readiness guard (all props must be set before request)
- Commit `0af549e`: Remove `requestIfNeeded()` from `token`/`index` props (only `assetId`/`pixelSize`)
- Commit `547c430` (tip): **Restore `requestIfNeeded()` on ALL props** (assetId, index, token, pixelSize)
- Current state: **Every prop change triggers `requestIfNeeded()`**

**Impact on simulator vs device:**
- **Hypothesis:** Prop-order race on simulator may set `token = 0` or `index = -1` before valid values arrive
- Multiple `requestIfNeeded()` calls per view may **cancel** pending requests prematurely
- Build 280's single-prop trigger (only `assetId`) was **deterministic** (last prop wins)
- PR #22's all-prop trigger is **non-deterministic** (depends on React prop commit order)

---

#### Change: Logging

**Build 280 baseline:**
- No logging in `PhotokitThumbView` props
- No logging in `PhotokitThumbsModule` open functions
- Silent failures

**PR #22 (547c430):**
- `print("[PhotokitThumb] Prop assetId: ...")` on every prop change (4 props × N views)
- `console.log` / `console.error` in TS wrapper (`PhotokitThumbView.ts`)
- Diagnostic warnings in `isPhotokitThumbsAvailable()`
- Session/asset lookup logging in Swift (commits `9756a73`, `6edcdc4`)

**Impact on simulator vs device:**
- Logging overhead may slow simulator more than device
- Diagnostic noise may reveal root cause (check Metro logs for "FAILED to load native module")

3. Rebuild and test

5. If still gray: not authorization

#### H5: Prop-Order Race Triggers Premature Cancellation

**Mechanism:**
- PR #22 tip (`547c430`) calls `requestIfNeeded()` on **every** prop change
- React Native may batch prop updates non-deterministically
- Possible order: `token=0 → requestIfNeeded()` → `token=123 → requestIfNeeded()`
- First request with `token=0` fails guard → no-op
- Second request with `token=123` starts, but immediately cancelled by `pixelSize` prop → `requestIfNeeded()`
- Result: churn of request starts/cancels, never completes → forever-gray

**Why device works:**
- Device CPU faster, prop batches apply atomically?
- Release build optimizations reduce prop-churn frequency?

**Falsification:**
1. Revert to commit `0af549e` (only `assetId`/`pixelSize` trigger `requestIfNeeded()`)
2. Keep everything else
3. Rebuild and test
4. If paints: all-prop triggering is causal
5. If still gray: not prop-order race

**Alternative test:**
1. Edit `PhotokitThumbView.swift`:
   - Remove `requestIfNeeded()` from `index`, `token`, `pixelSize` props
   - Keep only `assetId` prop trigger (like build 280)
2. Rebuild and test
3. If paints: prop-order race is causal
4. If still gray: not prop-order
